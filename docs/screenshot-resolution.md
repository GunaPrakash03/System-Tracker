# Reducing screenshot resolution

Screenshots are the only part of this system whose storage grows without bound.
This is what they cost today, what can be done about it, and what each option
actually saves — measured on a real capture from this deployment, not estimated.

## Where we are now

Captures are full-screen PNGs at the workstation's native resolution, uploaded
unmodified unless blurring is switched on for that employee.

| | |
|---|---|
| Capture resolution | the whole screen — 1600×900 on `sys0041` |
| Format | PNG, no downscaling, no re-encoding |
| Average full image | **141 KB** across 7,604 files |
| Average thumbnail | 23 KB across 1,512 files (the API makes these, not the tracker) |
| On the volume | 1.1 GB of 45.5 GB, 2% |

Two percent sounds comfortable. It is not, once the arithmetic is projected.

## Why it matters

At the current cadence of roughly one capture per minute:

| Scale | Per person / day | Per person / month | Ten people / month |
|---|---|---|---|
| Today (141 KB) | ~66 MB | ~1.4 GB | ~14 GB |

Ten workstations fill the 45.5 GB volume in **about three months**. Two fill it
in a bit over a year. The volume can be grown, but storage is the cost that
compounds — every image is kept, and nothing prunes them.

Reducing resolution is the lever with the best ratio of saving to lost value,
because a monitoring screenshot needs to show *which application was on screen
and roughly what was happening*, not to be legible.

## What each option saves

Measured on a real 1600×900 capture from this deployment, 234 KB as PNG,
rescaled through the same GdkPixbuf path the tracker already uses for blurring:

| Scale | Pixels | PNG | saving | JPEG q75 | saving |
|---|---|---|---|---|---|
| full | 1600×900 | 234 KB | — | 146 KB | 38% |
| 75% | 1200×675 | 201 KB | 14% | 87 KB | 63% |
| **half** | **800×450** | **88 KB** | **62%** | 49 KB | 79% |
| third | 533×300 | 68 KB | 71% | 23 KB | 90% |
| quarter | 400×225 | 37 KB | 84% | 14 KB | 94% |

Note how poorly 75% performs for PNG — 14% off the file for 25% off each axis.
PNG compresses runs of identical pixels, and a lightly scaled screenshot still
has large flat regions with resampling noise smeared through them. Halving is
where the curve turns.

### What they actually look like

Percentages do not tell you whether a screenshot is still useful. Samples of a
real capture at every scale, with 1:1 detail crops, are generated by the script
in "Producing samples" below. Inspecting them changes the advice:

| Scale | Legibility of the same terminal text |
|---|---|
| full | fully legible |
| half | **still readable with effort** — commands and tab titles decipherable |
| third | text collapses into shapes; you see *a terminal*, not what it says |
| quarter | only window layout and colour survive |

So half scale does **not** destroy legibility, as one might assume from a 62%
saving — a 14px monospace font survives it. Smaller interface text does not.
That makes the choice a question of intent rather than of storage alone:

- **Keep the record readable** — half, 800×450. About **62%** saved, and a
  screenshot that can still answer "what was on screen" in detail. This is the
  recommendation if screenshots are ever likely to be discussed with an
  employee, because an illegible image is hard to stand behind.
- **Reduce what is stored about people** — a third, 533×300. About **71%**
  saved, and text stops being readable while the shape of the work remains.
  Better still, pair half scale with the existing blur, which is deliberate
  about privacy rather than achieving it by accident of resolution.

Do not treat downscaling as a privacy control on its own. Blurring exists for
that, is applied before the image leaves the machine, and is irreversible.

## The recommended change

Add a downscale step before upload, using GdkPixbuf — which is already a
dependency (`python3-gi`, required for capture) and already used by
`blur_png()`, so this introduces nothing new and does not touch the stdlib-only
rule for `tracker/`.

A new config key, off by default so existing installs do not change behaviour
silently:

```json
"screenshot_max_width": 800
```

Zero or absent means "do not scale", which is today's behaviour. Any other value
scales proportionally so that the width does not exceed it; height follows the
aspect ratio, so mixed monitor sizes across a fleet all land at a comparable
cost.

Implementation, mirroring `blur_png()` in `tracker/proc_tracker.py`:

```python
def downscale_png(png, max_width):
    """PNG bytes scaled so width <= max_width, or the original on any failure.

    Storage is the only cost of a screenshot that grows without bound, and a
    monitoring capture needs to show which window was on screen rather than be
    readable. Half scale removes about 62% of the file while leaving window
    shapes, video and terminals recognisable.

    Unlike blur_png this returns the ORIGINAL on failure rather than None: a
    full-size screenshot is merely expensive, whereas an unblurred one breaks a
    promise made to the employee. Cost may degrade silently; privacy may not.
    """
    if not png or not max_width:
        return png
    try:
        import gi
        gi.require_version("GdkPixbuf", "2.0")
        from gi.repository import GdkPixbuf

        loader = GdkPixbuf.PixbufLoader.new_with_type("png")
        loader.write(png)
        loader.close()
        pb = loader.get_pixbuf()
        if pb is None:
            return png
        w, h = pb.get_width(), pb.get_height()
        if w <= max_width:
            return png
        nh = max(1, round(h * max_width / w))
        small = pb.scale_simple(max_width, nh, GdkPixbuf.InterpType.BILINEAR)
        if small is None:
            return png
        ok, buf = small.save_to_bufferv("png", [], [])
        return bytes(buf) if ok else png
    except Exception:
        return png
```

Call it at the same point blurring happens, **before** the blur:

```python
shot = downscale_png(shot, setting(cfg, overrides, "screenshot_max_width", 0))
# then the existing blur, if enabled for this employee
```

Order matters. Scaling first means the blur operates on a smaller image, which
is cheaper; and because blurring is itself a downscale-and-stretch, blurring
first then scaling would resample twice for no benefit.

## Options that need no code at all

**Capture less often.** Storage falls in direct proportion. The organisation's
screenshot frequency is a dashboard setting, and the tracker snaps any request
to a whole number of slot intervals. Going from every minute to every five cuts
storage by 80% — far more than any resolution change — at the cost of a coarser
record. This is the biggest lever, and it is already available.

**Turn blurring on.** Blur is implemented as downscale-then-upscale, so a
blurred PNG has far less detail to compress and lands much smaller than a sharp
one at the same dimensions. If privacy is wanted anyway, the storage saving
comes free with it.

## What not to do

**Do not switch to JPEG without thinking it through.** The savings are real —
79% at half scale against 62% for PNG — but the tracker posts the file as
`screenshot.png` and the API derives what it stores from that. Changing the
format means changing the upload filename, the content type, and confirming the
dashboard and thumbnailer both cope. It is a larger change than it appears, for
an extra 17 percentage points on top of what scaling already gives.

**Do not scale below a third.** At 400×225 a screenshot stops answering the
question it exists to answer: you can no longer tell one document from another,
and the record becomes hard to defend if it is ever the basis of a conversation
with an employee.

**Do not retrofit existing images.** The 7,604 files already stored could be
rescaled in place, but the database records their paths and the API serves them
by path; rewriting them saves about 700 MB on a volume that is 98% empty. Not
worth the risk.

## Producing samples

To judge a scale before committing to it, rescale a real capture through the
same code path the tracker uses and look at the result. Samples for this
deployment were generated into `~/screenshot-resolution-samples/`, which also
contains a `compare.html` showing every scale side by side with 1:1 detail
crops.

```python
import gi
gi.require_version("GdkPixbuf", "2.0")
from gi.repository import GdkPixbuf

pb = GdkPixbuf.Pixbuf.new_from_file("some-screenshot.png")
w, h = pb.get_width(), pb.get_height()
for name, div in (("half", 2), ("third", 3), ("quarter", 4)):
    small = pb.scale_simple(int(w / div), int(h / div), GdkPixbuf.InterpType.BILINEAR)
    small.savev(f"{name}.png", "png", [], [])
```

Judge on a **1:1 crop**, never on the whole screen fitted to a browser window —
the browser resamples it back up and hides exactly the detail loss you are
trying to assess.

## Applying it

Once implemented, the key can be set per workstation in
`~/.local/share/system-tracker/config.json`, or — better — added to the
per-employee settings the dashboard already writes, so it can be changed for the
whole fleet without touching any machine. The existing overrides mechanism
(`setting(cfg, overrides, …)`) already reads dashboard-supplied values, so
wiring it there is a matter of adding the field to Tracker Settings alongside
the screenshot interval and blur toggle.

Restart is not required. The tracker re-reads employee settings on a timer and
applies changes within about 60 seconds.
