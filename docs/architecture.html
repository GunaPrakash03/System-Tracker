Only System-Tracker is reachable from the internet. The API has no domain attached and Postgres has no TCP proxy, so neither exists as far as the outside world is concerned. Everything — dashboard, API calls, screenshot images — comes through one origin, which is why there is no CORS to configure.

The database stores a path, never the image

screenshot.file  (a relative path, in Postgres)
screenshots/2026/08/12/<tenantId>/<employeeId>/screenshots-1786511690-177.png

on disk, inside the volume
/srv/gauzy/apps/api/public/screenshots/2026/08/12/<tenantId>/<employeeId>/…png

what the browser asks for
https://system-tracker-production.up.railway.app/public/screenshots/2026/…png

Dated folders, then tenant, then employee. The same relative path is the database value, the location on disk and the URL suffix — so a file can be traced in either direction without a lookup table.

How one screenshot gets there

1The tracker captures the screen via GNOME's D-Bus screenshot service, blurring first if that employee's setting says so. A shot that fails to blur is dropped, never sent sharp.
2It posts the time slot, receives the slot id back, then posts the image to /api/timesheet/screenshot attached to that id — a screenshot with no slot behind it is stored but never renders.
3nginx proxies that through to the API on the private network.
4The API writes the file into the volume and inserts a row holding the relative path.
5The dashboard renders /public/<path>; nginx proxies that back to the API, which serves the file.

Two failure modes worth knowing. If the volume is not writable by node, the API answers HTTP 201 anyway and the tracker logs a success for an image that was never written — count rows in the database, do not trust the log. And without the /public/ proxy rule, nginx answers image requests with index.html and a 200, so every screenshot renders broken while nothing appears to fail.

Where the Docker images are stored

In a private GitHub Container Registry namespace. Railway never builds anything — it pulls a tag you pushed, which is why deploys take seconds rather than the half hour a build costs.

ImageContentsSize
ghcr.io/gunaprakash03/tracker-api NestJS API, modified Gauzy core ~1.7 GB
ghcr.io/gunaprakash03/tracker-webapp Compiled Angular bundle + nginx ~108 MB

Both are private, so each Railway service holds a GitHub token with read:packages to pull them. Tags are commit SHAs, never latest — Railway caches by digest, and a moved tag silently redeploys the previous build.

Every store, and what lives in it

StoreHoldsLost if…
Postgres
postgres-volume		 Employees, users, time slots, screenshot records, per-employee tracker settings, app-productivity rules, the daily usage summary the volume is deleted — this is the irreplaceable one
api-volume
/srv/gauzy/apps/api/public		 Screenshot image files and thumbnails the volume is deleted; the database then references files that no longer exist
ghcr.io Built API and webapp images, one tag per commit nothing operational — they rebuild from the repository
Each workstation
~/.local/share/system-tracker/		 The tracker itself, and config.json at mode 0600 holding that machine's credentials the machine is reimaged — reinstall from the bundle

Note where the tracker's own settings live: not in a config service, but in a single employee_setting row per person in Postgres, shared between the dashboard and the tracker. The dashboard writes the screenshot interval, idle threshold and department there; the tracker reads those and writes its daily usage summary back into the same object. Both sides merge rather than replace, because the endpoint overwrites the whole object.
