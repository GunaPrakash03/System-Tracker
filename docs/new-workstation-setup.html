System-Tracker · provisioning runbook

Setting up tracking on a new Ubuntu workstation

Six steps, roughly ten minutes. The tracker is stdlib-only Python, so there is nothing to compile and nothing to install with pip — one 40 KB archive and a single command do the whole job.

Target Ubuntu with GNOME Server system-tracker-production.up.railway.app Bundle system-tracker-2026-08-12.tar.gz

Before you start

  • An employee account of its own for this machine — created in step 1.
  • Shell access on the new machine as the person who will actually use it.
  • sudo once, only to install python3-gi.

Get a current archive — on the machine with the repository

This block is the only part that needs the repository. The new workstation never sees it: everything from step 2 onwards runs from the single archive file. Rebuild rather than reuse whatever is sitting in dist/ — the installer copies files verbatim, so a stale archive silently installs old code. 

cd ~/System-Tracker

# what is already there, and how old
ls -lh dist/

# rebuild from current source; the argument is just the version stamp
./packaging/build-bundle.sh 2026-08-12

# confirm the contents before sending it anywhere
tar tzf dist/system-tracker-2026-08-12.tar.gz
sha256sum dist/system-tracker-2026-08-12.tar.gz
Expected — a flat archive, no wrapper directory, about 40 KB 
./install.sh
./uninstall.sh
./tracker/proc_tracker.py
./tracker/report.py
./tracker/config.example.json
./tracker/README.md
./tracker/gnome-extension/system-tracker-shot@local/metadata.json
./tracker/gnome-extension/system-tracker-shot@local/extension.js

Keep the sha256sum output — step 2 compares against it to prove the copy arrived intact.

Run as the user, not as root

This is a per-user install with a systemd user service and a GNOME extension. Running install.sh under sudo puts everything in root's home, where it will never start.

1

Create an employee account for this machine

In the dashboard: Employees → Add, using the person's own email address and a password only they will use.

Do not reuse an existing account

Every time slot and screenshot is attributed to whichever employee the tracker logs in as. Two machines sharing one account merge into a single timeline, and there is no way to separate them afterwards.

The account must resolve to an employee, not merely a user — login fails otherwise and the service will restart forever without collecting anything.

For screenshots, switch on Allow Screen Capture for that employee under Settings → Tracker Settings. The tracker reads this from the dashboard on a timer, so it stays off until you enable it there.

2

Copy the bundle across

From the machine holding the repository:

# replace user@new-machine with the real host
scp ~/System-Tracker/dist/system-tracker-2026-08-12.tar.gz user@new-machine:~/

A USB stick works equally well — it is one small file with no dependencies of any kind.

Then, on the new machine, check what landed:

cd ~
ls -lh system-tracker-2026-08-12.tar.gz
sha256sum system-tracker-2026-08-12.tar.gz

# look inside without unpacking
tar tzf system-tracker-2026-08-12.tar.gz

The checksum must match the one from Before you start. If it differs the copy is truncated or corrupt — send it again rather than pressing on, because a partial archive extracts without complaint and fails later in ways that look like a configuration problem.

3

Install the one prerequisite

On the new machine:

python3 --version            # needs 3.8 or newer; Ubuntu ships this
sudo apt install -y python3-gi
echo "$XDG_SESSION_TYPE"     # x11 or wayland — both are supported

python3-gi is the only package required, and only for screenshots. Process and activity tracking work without it.

4

Run the installer

The archive has no wrapper directory, so it unpacks straight into wherever you are — no folder to enter, no flags to remember. Then run the installer with the email and password from step 1: 

cd ~
tar xzf system-tracker-2026-08-12.tar.gz
ls -l install.sh uninstall.sh tracker/

GAUZY_URL=https://system-tracker-production.up.railway.app \
GAUZY_EMAIL=newperson@youngglobes.com \
GAUZY_PASSWORD='their-password' \
./install.sh
Three things land in the home directory 
install.sh    uninstall.sh    tracker/

Extract from the terminal, not the file manager

Because the archive has no single root, GNOME's Archive Manager will wrap it in a folder of its own to avoid scattering files — which is the folder you were trying to avoid. The tar xzf line above does the right thing.

Quote the password

The single quotes around it are not optional. Passwords containing $, !, & or a space will otherwise be mangled by the shell before the installer ever sees them, and the failure surfaces later as a login error that looks like a wrong password.

That single command:

  • installs the tracker to ~/.local/share/system-tracker/
  • writes config.json at mode 0600, credentials included
  • installs and enables the silent-screenshot GNOME extension
  • creates and starts a systemd user service that auto-starts at login

The installer copies what it needs, so once step 6 confirms the service is running you can clear the home directory again: 

rm -rf ~/tracker ~/install.sh ~/system-tracker-2026-08-12.tar.gz

Keep uninstall.sh

It is self-contained — it touches only ~/.local/share and systemd, and needs none of the files above. Leave it in the home directory and removal stays a one-liner later.

5

Log out and back in, once

GNOME will not load a newly installed extension into a session that is already running. If the installer warned that it could not enable the extension, log out, log back in, and then: 

gnome-extensions enable system-tracker-shot@local

Skip this and everything works except screenshots.

6

Watch it come up

systemctl --user status system-tracker
journalctl --user -u system-tracker -f
What success looks like, within a minute or two 
Login https://system-tracker-production.up.railway.app as newperson@youngglobes.com ...
OK. employee=8f21c4de | interval 60s, focus sample 5s
screenshots: controlled by the dashboard toggle (Allow Screen Capture) — currently ON
ACTIVE 100% (60/60s) | 18 apps, on-screen: chrome | 2 tabs | shot 240KB

If you see “login failed”, stop here

The credentials are wrong, or the account has no employee record. The service will restart on a loop and collect nothing at all — it is not a slow start, and waiting will not fix it. Go back to step 1.

Then confirm it reached the server

Open Employees → that person → Activity in the dashboard and check that both a time slot and a screenshot have appeared.

The local log is not proof of storage

When the API cannot write to its volume it still answers HTTP 201, so the tracker logs shot 240KB for a screenshot that was never saved. This is a real failure we hit in production. Verify in the dashboard, not in the journal.

Two things worth knowing

Rebuild the bundle whenever the tracker changes

./packaging/build-bundle.sh 2026-08-12 from the repository root. The installer copies files verbatim, so a stale archive silently ships old code — the one checked into dist/ was seven commits behind when this guide was written.

Windows machines take a different route

This tracker is Linux-only by design: it depends on /proc, X11 or Mutter, and GNOME's screenshot service. On Windows, install the official Ever Gauzy Desktop Agent instead — it reports into the same instance, so the dashboard stays unified.
