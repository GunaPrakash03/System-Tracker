1

Built and pushed the two images

Both images are built locally and deployed by tag — Railway never builds them. The webapp image had never been pushed at all; its registry repository did not exist. 

cd ~/System-Tracker/gauzy
SHA=$(git rev-parse --short HEAD)          # the tag, for both images
docker login ghcr.io                        # once; the token needs write:packages

# webapp — the Angular bundle and the nginx config
docker buildx build -f .deploy/webapp/Dockerfile \
  --build-arg NODE_ENV=production \
  --build-arg NODE_OPTIONS=--max-old-space-size=7168 \
  --build-arg GAUZY_APP_COMMIT=$SHA \
  -t ghcr.io/gunaprakash03/tracker-webapp:$SHA --load .

docker push ghcr.io/gunaprakash03/tracker-webapp:$SHA

# api — packages/core, packages/contracts, the NestJS server
docker buildx build -f .deploy/api/Dockerfile \
  --build-arg NODE_ENV=production \
  --build-arg NODE_OPTIONS=--max-old-space-size=7168 \
  --build-arg GAUZY_APP_COMMIT=$SHA \
  -t ghcr.io/gunaprakash03/tracker-api:$SHA --load .

docker push ghcr.io/gunaprakash03/tracker-api:$SHA

Tag with the commit, never latest

Railway caches by digest, so a moved latest silently redeploys the previous build. The heap is set to 7 GB here rather than the runbook's 12 GB because this machine had 8 GB free.

Check disk and memory first — both fail late

The Angular build asks for a 7 GB heap and the API image lands at roughly 3.4 GB, so a box that is short of either will spend a long time before failing. On 13 August this machine had 8.3 GB of disk free at 98 % full and 5.2 GB of memory available — neither was enough. 

df -h /                 # want well over 10 GB free
free -h                 # want more than the 7 GB heap
docker system df        # where the space has gone

docker builder prune -af # build cache only — safe; ~29 GB reclaimable

Browsers are usually the memory culprit; Chrome alone held 10.9 GB here. For disk, prune the build cache only. This box also hosts unrelated projects — ddev-*, drupal-mariadb, abi-*-mariadb among 59 volumes — so docker volume prune and docker image prune -a would take those with them.

Registry credentials are a UI-only step

The images are private, and Railway's API does not expose registry credentials. The service failed to deploy with no build and no deploy logs at all until a GitHub token with read:packages was pasted into Settings → Source → Registry Credentials. That signature — zero logs — means the image pull failed before any container started.

The stock CMD uses an entrypoint that serves static files with no /api/ proxy. The compose entrypoint is the one that writes the proxying config, and Railway's start command overrides CMD — which is exactly enough, because the image entrypoint is a pass-through.

Branding is runtime, not source

The Dockerfile hardcodes Ever's company name as an image default, overriding what the source says. Changing the footer needed only a Railway variable — no rebuild.

4

Loaded the screenshot store

The database already held the screenshot records; the image files had never left this machine. 8257 files, 959 MB, streamed into the volume over SSH. 

railway ssh keys add            # once, from the ssh agent

tar -C ~/ever-gauzy/apps/api/public -cf - screenshots \
  | railway ssh --service api --environment production -- \
      tar xf - --no-same-owner -C /srv/gauzy/apps/api/public

railway ssh --service api -- chown -R node:node /srv/gauzy/apps/api/public

The chown is not optional

The API runs as node and the volume is created owned by root, so uploads fail with EACCES — and the API answers HTTP 201 anyway, so the tracker logs a success for an image that was never written. Any newly created volume needs this.

The installer puts the tracker in ~/.local/share/system-tracker/, writes the config at mode 0600, installs the silent-screenshot GNOME extension, and registers a systemd user service that starts at login.

Three fixes this first real install forced

The bundle could not install as shipped: the installer resolved its sources one directory too high, the archive nested everything under a wrapper folder, and the example config recorded local time against an API that stores UTC — putting every slot five and a half hours in the future. Use a bundle built after those fixes.

7

Moved the screenshot store to S3

13 August. Not a migration — a configuration change. screenshot.entity.ts has always stored a storage key and computed fullUrl virtually on read, so there was no column of stale links to rewrite and no schema change of any kind. The tracker was untouched too: it posts bytes and the server decides where they go.

VariableValue
FILE_PROVIDERS3 — replacing LOCAL
AWS_S3_BUCKETsystem-moniter
AWS_REGIONus-east-1
AWS_ACCESS_KEY_ID
AWS_SECRET_ACCESS_KEY		a dedicated IAM user, scoped to this bucket
AWS_S3_FORCE_PATH_STYLEfalse — virtual-hosted URLs, the AWS default

The variables belong to api, not to the webapp

They were first set on System-Tracker, which runs nginx and never touches S3, so they sat there inert while screenshots carried on landing on the volume. The service that receives POST /api/timesheet/screenshot and writes the files is api. Nothing reports this as an error; the only symptom is that nothing changes.

The tenant setting overrides the variable, silently

setProvider() in file-storage.ts reads tenantSettings.fileStorageProvider first and only falls back to FILE_PROVIDER when that is empty or invalid. The tenant was pinned to LOCAL, so all six variables would have been ignored with nothing in the log to say so. It was flipped to S3 in the database — the dashboard's Settings → File Storage writes the same row.

The per-tenant AWS credential fields on that page are deliberately left blank: they only override when non-empty, so blank keeps the Railway variables authoritative. Credentials in the database are harder to rotate and end up in backups.

The bucket stays private. url() returns a presigned link with expiresIn: 3600, regenerated on every read — presigning is what serves the images, and a public bucket would expose every employee's screen to anyone who guessed a key. Note also that the S3 provider builds its client with no endpoint, so it reaches Amazon and nothing else; R2, MinIO and Railway's own object storage would need the WASABI or DIGITALOCEAN provider.

The 2390 rows written before the switch still say LOCAL — storageProvider is stored per row, so changing the provider moves nothing retroactively. They resolve against the volume and will break the moment it is detached. Deleting them, and the 1.1 GB they point at, is still outstanding.

8

Two defects the move surfaced

Both were latent long before 13 August. Switching provider is simply what gave them something to break.

A redeployed API left the proxy pointing at a dead address

Setting the variables redeployed api, and Railway hands a service a new private IPv6 address each time it deploys. nginx resolves the hostname in an upstream block once, at startup, and keeps that address for the life of the worker — so the webapp spent twenty minutes proxying to an address that no longer answered.

It does not look like an outage

Static files keep serving from disk, so the dashboard loads normally and only the data is missing — indistinguishable at a glance from a broken API. The API was in fact healthy throughout and answering /api/health from inside the private network. Trackers, meanwhile, crash-looped on login timeouts. Redeploying the webapp cleared it by forcing a fresh resolve.

Fixed at the source: the upstream block is gone and proxy_pass now names the target through a variable, which forces nginx to resolve per request. That needs an explicit resolver, which nginx will not take from /etc/resolv.conf itself, so entrypoint.compose.sh reads the first nameserver out of that file and substitutes it in — bracketed when it is IPv6, as Railway's fd12::10 is.

Screenshots downloaded instead of opening

Both S3 upload paths stored a media type no browser can render. The multer engine set none, so multer-s3 fell back to application/octet-stream; putFile hardcoded the literal string image, which is not a media type at all — it has no subtype. Its Content-Disposition was malformed too, omitting the filename= parameter.

Why LOCAL never showed this

Serving from the volume, the API derived the header from the file extension on every read. S3 stores what it is given at upload time and serves it back verbatim, so the bug had nothing to break until the provider changed. The dashboard looked correct throughout, because <img> sniffs the bytes and renders regardless — only a top-level navigation trusts the header.

Objects already in the bucket were repaired in place with aws s3 cp --metadata-directive REPLACE; a code fix only reaches new uploads.

Pushing the images is not deploying them

Both services were on Builder: RAILPACK with the repository connected, so every git push triggered a Railway build from source. Railpack does not use .deploy/webapp/Dockerfile — it autodetects a Node app, which never listens on 4200, so the health check on / failed eleven times and the deploy was marked FAILED. Three consecutive deploys failed that way and the dashboard stayed down for about four hours, while the images built locally sat unused in the registry. Pointing the service at the image is a separate act from pushing it.

What was actually run, once both images were pushed. The service source must be set to the image, which is what takes it off the repository builder:

At the time this was done, setting the source image was believed to have no railway CLI equivalent, so it was performed as Settings → Source in the dashboard. That is no longer true — CLI 5.37.2 has railway service source connect --image, used in step 9 below. Either way the point stands: setting the source is what replaces the repository connection, and the redeploy below only restarts the service with whatever source it already has. 

# 1. webapp FIRST — it carries the resolver fix that makes step 2 safe
#    Settings -> Source -> ghcr.io/gunaprakash03/tracker-webapp:39f50b2
railway redeploy --service System-Tracker --environment production --yes

#    verify the fix is live in the container that came up
railway ssh --service System-Tracker -- \
  grep -nE "resolver|api_upstream" /etc/nginx/nginx.conf
#    -> resolver [fd12::10] valid=10s;
#    -> set $api_upstream "api.railway.internal:3000";

# 2. api — only now, and only after / and /api/health both return 200
#    Settings -> Source -> ghcr.io/gunaprakash03/tracker-api:aa8885f
railway redeploy --service api --environment production --yes

The order paid for itself immediately

Redeploying the API moved its private address exactly as before. This time the webapp was already resolving per request, so the public URL showed a single ~20 second gap on /api/health — the container restart itself — and recovered with no intervention. The morning's identical event cost twenty minutes and a manual webapp redeploy. The dashboard at / never dropped below 200 throughout.

Both fixes were confirmed live rather than assumed:

# the site, through the API redeploy
curl -s -o /dev/null -w "%{http_code}\n" \
  https://system-tracker-production.up.railway.app/api/health

# and a capture written AFTER the API came up on the new image
aws s3api head-object --bucket system-moniter \
  --key <newest-key> --query ContentType --output text
-> image/jpeg

Screenshots taken after the deploy report image/jpeg and open in the browser instead of downloading. The tags differ by one commit — 39f50b2 for the webapp, aa8885f for the API — because HEAD moved between the two builds. Of the twenty commits separating the API's previous image from aa8885f, exactly one touches API code, so the jump is the Content-Type fix and nothing else. The shorter presigned-URL expiry in 39f50b2 is API-side and is therefore still waiting on the next API build.

9

14 August — the dashboard trim, and the half-fixed builder

Commit cd1d76d removes the Human Resources dashboard tab, trims Settings to Tracker Settings / Danger Zone / AI Providers, makes a user's own profile read-only for EMPLOYEE and MANAGER, and drops Forgot password? from the login page. Both images were built and pushed as before.

The repository builder was only ever taken off api

The fix recorded in step 8 was applied to one service. api moved to image deploys and stayed there — it went to tracker-api:cd1d76d and reported SUCCESS with an empty commit column, which is what an image deploy looks like. System-Tracker kept its repository connection, so the git push behind cd1d76d started a Railpack build of the whole monorepo. Two of them sat in BUILDING (05:07 for acd9fde, 05:34 for cd1d76d) while the pushed webapp image went untouched and the service source still read tracker-webapp:39f50b2.

The tell is the commit column in railway deployment list. A hash there means Railway built from the repository; - means it pulled the image. That single column distinguishes the two states faster than any log does.

Disconnecting the source is the step that was missing. Reconnecting by image without it leaves the repository trigger in place: 

# 1. branding — the image bakes ENV PLATFORM_LOGO=logo_Gauzy.svg and the
#    entrypoint substitutes the CURRENT environment at every start, so an
#    unset variable means the Ever mark. --skip-deploys: do not deploy the old image
railway variable set --service System-Tracker --skip-deploys \
  PLATFORM_LOGO=assets/images/logos/logo_young_globes.png \
  NO_INTERNET_LOGO=assets/images/logos/logo_young_globes.png \
  GAUZY_CLOUD_APP= \
  GAUZY_CLOUD_ENDPOINT=

# 2. stop the stuck Railpack build
railway down --service System-Tracker --yes

# 3. drop the repository source — what step 8 missed on this service.
#    Without this, connecting an image leaves the repo trigger in place and
#    the next push starts another Railpack build over the top.
railway service source disconnect --service System-Tracker

# 4. point it at the pushed image (webapp FIRST, per step 8)
SHA=$(git -C ~/System-Tracker rev-parse --short HEAD)

railway service source connect \
  --image ghcr.io/gunaprakash03/tracker-webapp:$SHA \
  --service System-Tracker

railway redeploy --service System-Tracker --environment production --yes

# 5. api — only after / and /api/health both return 200. Whether this one
#    matters depends on the commit: cd1d76d touched no packages/core and was
#    deployed only to pick up 39f50b2's presigned-URL expiry, whereas
#    85651d4 adds employee.employeeCode and a migration, so the API image is
#    where the change actually lives.
railway service source connect \
  --image ghcr.io/gunaprakash03/tracker-api:$SHA \
  --service api

railway redeploy --service api --environment production --yes

Three settings to re-check after reconnecting a source

Disconnecting can reset service configuration, and two of these are load-bearing. The start command must remain ./entrypoint.compose.sh nginx -g "daemon off;" — without it the container never runs the entrypoint that substitutes PLATFORM_LOGO, API_BASE_URL and the rest into the compiled bundles, and the result is a site that serves but shows the Ever logo and cannot reach the API. The health check path stays /. The root directory /gauzy is a repository-build artifact and should be cleared, since it means nothing to an image deploy.

The registry is private, and the credentials are not in the CLI

An anonymous pull of tracker-webapp:<tag> returns 403. service source connect has no flag for registry credentials, so a reconnect can drop them and the first deploy then fails on image pull. As in step 3, that is a UI-only field: Settings → Source, ghcr username and token. Expect it rather than debug it.

The branding variables in step 1 above are the actual fix for the Ever logo on the login page, and no rebuild delivers it. Editing packages/ui-config/…/environment.prod.ts does nothing at all: that file is gitignored and regenerated by .scripts/configure.ts on every yarn config. Its defaults were corrected in .scripts/env.ts in the same commit, which fixes non-Docker builds — but the Docker path compiles a DOCKER_PLATFORM_LOGO placeholder and resolves it from the environment at container start, so on Railway the service variable is the only thing that decides.

Dashboard, API and trackers all answer on one origin: system-tracker-production.up.railway.app Neither the API nor Postgres is reachable from outside; the API has no domain and Postgres has no TCP proxy. Screenshots live in a private S3 bucket and are served only through presigned URLs that expire after an hour.
