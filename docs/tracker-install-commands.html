System-Tracker · new Ubuntu machine

Six commands, and what each one does

Run them in order from the home directory, as the person who will use the machine. Only the third needs sudo.

1

Check the archive arrived intact

sha256sum system-tracker-2026-08-12.tar.gz

Compare the output against the checksum from the machine you copied it from. A truncated or corrupt archive still extracts without complaint and then fails later in ways that look like a configuration problem — so it is worth thirty seconds here rather than an hour afterwards. If the two do not match, copy it again instead of continuing.

2

Install the one dependency

sudo apt install -y python3-gi

The tracker is stdlib-only Python — no pip, no compiler, no build. python3-gi is the single exception, and it is needed only for screenshots; process and activity tracking work without it. If the machine reports it is already installed, nothing happens and that is fine.

3

Unpack it

tar xzf system-tracker-2026-08-12.tar.gz

The archive is flat, so this drops three things straight into the home directory — install.sh, uninstall.sh and tracker/ — with no folder to enter first. Silence means success; tar prints nothing when it works.

Use the terminal, not the file manager. Because the archive has no single root folder, GNOME's Archive Manager wraps it in one of its own to avoid scattering files — which puts you back where you started.

4

Install and connect to the server

GAUZY_URL=https://system-tracker-production.up.railway.app \
  GAUZY_EMAIL='their-email' \
  GAUZY_PASSWORD='the-password-you-set' \
  ./install.sh

One command does everything: copies the tracker to ~/.local/share/system-tracker/, writes its config at mode 0600 with these credentials, installs the silent-screenshot GNOME extension, and registers a systemd user service that starts automatically at login.

Run it as the user, never with sudo. It is a per-user install with a user-level service; under sudo everything lands in root's home, where it will never start.

Give this machine its own employee account. Activity is attributed to whoever the tracker logs in as, so two machines sharing an account merge into one timeline that cannot be separated afterwards. And keep the quotes — a password containing $, !, & or a space is mangled by the shell before the installer sees it, then looks like a wrong password later.

5

Check it is running

systemctl --user status system-tracker

You want active (running). Beware the trap here: a crash-looping service also reports as running, because systemd keeps restarting it. The number that matters is the restart count — if it climbs each time you look, the service is failing and step 6 will say why.

6

Watch what it is actually doing

journalctl --user -u system-tracker -f
Success, within a minute or two 
Login https://system-tracker-production.up.railway.app as person@youngglobes.com ...
OK. employee=8f21c4de | interval 60s, focus sample 5s
screenshots: controlled by the dashboard toggle (Allow Screen Capture) — currently ON
ACTIVE 100% (60/60s) | 18 apps, on-screen: chrome | 2 tabs | shot 240KB
Failure — stop here, do not wait it out 
RuntimeError: login failed (HTTP 0): <urlopen error [Errno 111] Connection refused>
Scheduled restart job, restart counter is at 974.

A login failure is fatal, not slow: the tracker exits, systemd restarts it, and it collects nothing at all while doing so. Either the credentials are wrong or the account has no employee record. Press Ctrl+C to stop following the log.

Two things afterwards. Log out and back in once, then gnome-extensions enable system-tracker-shot@local — GNOME will not load a new extension into a running session, and without it screenshots still work but are not silent. Then confirm in the dashboard under Employees → that person → Activity. The tracker's own log is not proof a screenshot was stored.
